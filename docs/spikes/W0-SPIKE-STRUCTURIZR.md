# W0-SPIKE-STRUCTURIZR — Structurizr JSON/DSL sources, schema and export/import mapping

Date: 2026-11-12 · Environment: Linux 6.18.44 x86_64, Node v22.23.4, git 2.43.0, Python 3.13.18 (no JVM/Maven Central access)

## Question
Where the authoritative Structurizr JSON workspace schema and DSL reference live, what their exact property names / constructs are, and which subset designPerspectives should export (DSL + JSON) and import (JSON) in the first version. Informs the Structurizr exporter/importer contract.

## Not verified
- `sample.workspace.dsl` was not parsed by the Structurizr DSL parser, and `sample.workspace.json` was not loaded by `structurizr-client` (needs Java 21 and Maven Central; shell network is limited to npm and GitHub). The JSON was checked only against the OpenAPI schema by `validate.py`.
- Whether `structurizr/json` and `structurizr/dsl` were deleted, renamed or made private (GitHub API was not available for these repositories).
- Licence of the documentation prose in `structurizr.github.io` (only the theme's MIT file is present).
- Existence and quality of third-party non-Java DSL parsers (not searched; outside the git-first evidence rule and the timebox).
- Exact form of `structurizr.dsl.identifier` under `!identifiers hierarchical` (the sample assumes the dotted path), and whether the Java loader rejects unknown JSON properties.
- `deploymentGroups`, `customViews` and `customElements` JSON shapes (present in Java / DSL reference, absent from `structurizr.yaml`).
- Whether the Java loader requires default tags (`Element`, `Person`, ...) to be present on import, or re-derives them.

## Recommendation
Evidence: the only public, current source is `structurizr/structurizr` (Apache-2.0); the JSON contract is an OpenAPI 3.0 file (`info.version` 6.1.0) that omits fields the Java model serialises; the DSL parser is Java 21 only; DSL has no layout coordinates and no keyword found for `interactionStyle`; ids are strings, relationships are nested in their source element, tags are one comma-separated string. Interpretation: (1) pin the schema to `structurizr/structurizr@ad34036` `structurizr-json/structurizr.yaml` and hand-write TypeScript types/zod validators from it rather than generating from JSON Schema; (2) treat JSON as the lossless interchange format and DSL as a readable, lossy export (no layout, sync/async as a tag); emit `!identifiers hierarchical`, `!impliedRelationships false`, explicit view keys, explicit `include` lists; (3) first-version JSON import subset: `name`, `description`, `properties`; `model.people`, `softwareSystems` → `containers` → `components` with `id,name,description,technology,tags,url,group,properties,perspectives`; `relationships` with `id,sourceId,destinationId,description,technology,interactionStyle,tags,properties,linkedRelationshipId` (implied relationships imported as derived, not authored); `deploymentNodes` (`children`, `infrastructureNodes`, `containerInstances`, `softwareSystemInstances`, `environment`, `instances`); views `systemLandscapeViews`, `systemContextViews`, `containerViews`, `componentViews`, `deploymentViews` with `key,title,description`, scope id, `elements[{id,x,y}]`, `relationships[{id,vertices}]`; `documentation.decisions` (`id,date,status,title,content,format,elementId`) at workspace/system/container/component level. Read-and-preserve (round-trip untouched, not interpreted) for everything else: `dynamicViews`, `filteredViews`, `imageViews`, `views.configuration` (styles, themes, terminology), `documentation.sections/images`, `animations`, `healthChecks`, `configuration`, unknown keys such as `customElements`, `revision`, decision `links`. (4) Conventions needed because Structurizr has no equivalent: dataStore/queue/topic as container + reserved tag; relationship kind and owners as `properties` (owners optionally mirrored as a perspective); designPerspectives ids in a property. Risks: schema drift (schema version lags the library and is incomplete; unknown keys must be tolerated); default-tag handling on import/export; comma in tag names; numeric-string id convention of other tools vs. designPerspectives slugs; DSL export not machine-verified until a JVM job with the upstream parser is added to CI; many-to-many ADR↔element links collapse to one `elementId`; upstream consolidated its repositories in 2026, so URLs in older documentation (including links inside the current docs to `structurizr/java`) are stale.
