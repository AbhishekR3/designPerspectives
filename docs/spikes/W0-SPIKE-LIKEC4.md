# W0-SPIKE-LIKEC4 — LikeC4 as native DSL behind `ModelPort`

Date: 2026-11-12 · Environment: Linux x86_64, Node v22.23.4, npm 10.9.9, system `dot` 2.43.0 (2 cores, 7 GB, other installs running in parallel)

## Question

Can LikeC4 serve as the native on-disk C4 model DSL of designPerspectives, reached only through an internal `ModelPort` adapter, with the tool owning the `.c4` files and writing them with its own canonical printer (model object -> DSL text) followed by a re-parse with LikeC4? The result informs accept/reject of ADR-0004 ("LikeC4 as native DSL") and confirms or rejects the write path.

## Method

Packages inspected or run:

- `@likec4/language-services@1.60.0` (installed in `spikes/likec4/min/`, 77 packages; pulls `@likec4/core`, `@likec4/language-server`, `@likec4/layouts`, `@likec4/generators`, `@likec4/config`, `@likec4/log` at 1.60.0, `langium@4.4.0`, `@hpcc-js/wasm-graphviz@1.29.2`).
- `npm view` metadata only (not installed): `@likec4/diagram@1.60.0`, `@likec4/mcp@1.60.0`.

Commands:

### Prototype result: canonical printer and round trip

Printer input and output:

- `printer.mjs` takes `{ specification, elements[], relationships[], deployments[], views[] }` and returns four files: `spec.c4`, `model.c4`, `deployment.c4`, `views.c4` (164 lines for the fixture). Elements are nested by FQN and sorted by id; relationships are all top-level with full FQNs, sorted by source, target, kind, title; metadata keys and tags are sorted; all strings are single-line double-quoted with `\\ \" \n \t \r` escapes; Markdown values use `"""`. View rules and dynamic steps keep their given order.
- Elements, relationships and deployments are built from `out/model.json` (computed model). View rules are not present in the computed model (computed views contain only `nodes`/`edges`), so `views[]` is built from `parsedModel()` (`out/parsed.json`).

Evidence, `node roundtrip.mjs` (fixture):

- Print twice: byte-identical. Print with all input arrays reversed: byte-identical. No CR bytes, no trailing spaces, every file ends with LF.
- Reload of `out/printed/` with `LikeC4.fromWorkspace`: 0 errors.
- Elements 18/18, relationships 14/14 (keyed by source, target, kind, title), deployment elements 8/8, parsed view rules/steps 5/5, computed element styles 18/18, specification, computed view node/edge sets 6/6: 0 missing, 0 extra, 0 changed.
- Fixpoint: `print(reload(print(x)))` equals `print(x)` byte for byte.
- Not preserved: comments, original file split, original declaration order, relationship ids (0 of 14 unchanged), layout geometry (5 of 6 views changed, finding 5d), computed view `hash` (5 of 6 unchanged).

Evidence, `node roundtrip.mjs --nasty` (adds 17 elements and 8 relationships with difficult strings):

- Survived unchanged in title, technology, description (txt and md), metadata value, metadata array and relationship title: double and single quotes, literal backslashes, embedded newlines with indentation, `"""` and `'''` inside text, non-ASCII text, `} // { #tag -> x`, tab, a two-line title.
- Lost: leading and trailing whitespace in every string field (`"  leading and trailing  "` -> `"leading and trailing"`). This also changed the relationship key that included the title, and it is the only reason the fixpoint check was false in this mode.

What the prototype printer does not cover (it throws on these rather than printing something wrong): view predicates other than `*`, element refs and `.*`/`.**`/`._` selectors (for example `where`, `with`, relationship predicates `a -> b`), global styles and predicate groups, dynamic-view `parallel`/`alt`/nested steps and step properties, relationship `style`, element-level `style`/`icon` overrides (only kind-level `style` in `specification` is printed), tag colours, custom colours, `navigateTo`, deployment-level relationships, multi-project workspaces and `imports`. Elements merged through `extend` would be flattened into the single definition.

## Not verified

- Running inside an Electron main or utility process. Electron was not installed. Open points: the Node version bundled with the chosen Electron release against the declared floor `>=22.22.3`; loading ESM-only packages from the main/utility process; loading the Graphviz WASM from inside an asar archive.
- Layout determinism across operating systems, CPU architectures or Node versions. Only repeated runs on this Linux x64 machine were compared.
- Rendering with `@likec4/diagram`. Only the type declarations were read; the package was not installed or built, and its behaviour without `LikeC4ModelProvider` or the Vite plugin is unknown.
- `@likec4/mcp` contents and tools. Only registry metadata was read.
- Watch mode (`watch: true`), incremental reload (`onModelUpdate`) and the language server over LSP were not exercised.
- `generate()` from `likec4/generators/likec4` was not called directly; only `toDSL()`, which is documented as using the same output, was run.
- Whether `remeda` is the only dependency whose caret range resolves to an incompatible version; the scan stopped after the first failure was fixed by the override.
- Peak memory with `/usr/bin/time -v` (tool absent); the `dot` child process memory in `binary` mode is not included in the reported RSS.
- Behaviour on models larger than 610 elements, and layout time for single large views (the synthetic views had at most about 20 nodes each).
- Licence texts of code pre-bundled inside `likec4/dist` were not inspected.

## Recommendation

Evidence. LikeC4 1.60.0 is MIT-licensed, released 8 times in the last 6 months, and exposes a Node API that loaded the fixture from a directory and from in-memory strings, returned a computed model with all fields the claims list, and returned headless laid-out views that were byte-identical over three runs with the default WASM engine. Custom element and relationship kinds, tags, dynamic views and a deployment model loaded without errors, and LikeC4 imposed no nesting rules beyond rejecting parent-child relationships. The prototype printer produced byte-identical output on repeated and re-ordered input, and the print -> re-parse round trip preserved every compared element, relationship, deployment and view field on the fixture; under adversarial strings the only loss was leading/trailing whitespace. An upstream printer exists (`toDSL`, `writeDSL`, `generators/likec4`), is documented as lossy, and on this fixture produced output that re-parsed with 2 errors and was not stable across generations. Three observations bear on the plan: relationship ids changed on every re-print, layout geometry changed when declaration order changed, and the unbundled `@likec4/*` packages failed at runtime until `remeda` was pinned.

Interpretation. The evidence supports accepting ADR-0004 and keeping the write path "own canonical printer, then re-parse with LikeC4", with these conditions recorded in the ADR: (1) the core keeps its own relationship identity (for example source, target, kind, title or an id stored in `metadata`) and never persists LikeC4 relationship ids; (2) the adapter trims strings before printing, or the model contract states that string fields are trimmed, so that the round trip is exact; (3) canonical sorting is treated as a layout-affecting decision — it is stable once applied, but adopting a hand-ordered file will move diagrams on first save, so either sorting is accepted as the tool's rule or the printer preserves a stored order; (4) the dependency is taken either as the bundled `likec4` package (128 MB, includes Vite and Playwright) or as `@likec4/language-services` (about 48 MB) with a committed lockfile and a `remeda` override, the second being the better fit for an Electron app on size grounds; (5) view rules must be carried in the tool's own model or read from `parsedModel()`, because the computed model does not contain them; (6) the WASM engine is fixed as the layout engine, since the `dot` binary gives different geometry. The upstream `toDSL`/`generators/likec4` printer should be listed in the ADR as a considered alternative and not adopted now, because of the two defects seen and because its output order and format are not under the tool's control. The Electron runtime question is not answered by this spike and should be closed by the Electron spike before the ADR is marked final.
