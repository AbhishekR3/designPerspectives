## Goal

BMO reviews the design and the code in three ways:
- it checks them against the anti-patterns you choose;
- it checks them against the decisions (ADRs) the architects accepted, to find a decision that is broken or violated;
- it proposes characteristic ratings.

(A fourth way, suggesting risks, waits for Wave 10, which is parked.)

Every result is cited, labelled and shown next to what dp found by itself. Nothing is written until you press an action.

## Design [Proposal; rewritten after the owner answers]

1. **Task `antipattern-review`** (★Q11.1).
   - **Selectors:**
     - `entries`: library slugs, with the ones marked `check: true` pre-selected;
     - `scope`, which is required: a diagram, the selected elements, a container, or a draft.
   - **Context pack** (Wave 1), with the library entries' text in data blocks:
     - the model text for the scope;
     - the deterministic findings (Wave 8);
     - coupling numbers and cycles (Wave 7) and the scope's key code (Wave 5);
     - notes and decisions;
     - the entries' text;
     - code excerpts for the scope, through the file gate.
   - **Answer**, per entry:
     - a verdict: present, possible, not found, or can't tell;
     - statements with cites, checked by the Wave 1 verifier;
     - a suggested remedy.
   - **UI.**
     - A "Check against anti-patterns" button, on the Rules page and in the diagram's right-click menu.
     - An entry picker.
     - A results sheet showing dp's own findings beside BMO's verdicts, with disagreements pointed out ("dp found a cycle; BMO says not found").
2. **Actions on a result** (★Q11.2). Each result offers:
   - add as a checklist item;
   - add as linked work (DEC-085);
   - add as a comment (DEC-049).

   Nothing is written until an action is pressed.
3. **Task `propose-ratings`** (Q11.3).
   - Takes a scope.
   - For each characteristic it proposes current and needed stars, with a cited reason.
   - Each row is accepted on its own, into `dp.characteristics`. Engineers accept into a draft.
4. **Task `check-decisions`** (questions C7, option 3).
   - **Selectors:** `decisions` (accepted decisions; all in scope by default) and `scope`, required, as in task 1.
   - **Computed signal first.** A decision whose Compliance section names a rule shows "possibly violated" when that rule has a Finding on one of the decision's targets. This is computed, with no BMO.
   - **BMO's part.** Per decision: a verdict (holds, possibly violated, can't tell), with cited statements from the decision text, the model, the code excerpts and the decision's own alternatives and triggers. A decision without a Compliance rule is checked by BMO only, and labelled proposed.
   - **UI.** A button on the Decisions page and in a decision's panel; the sheet shows dp's computed signal beside BMO's verdict and points out disagreements.
   - **Actions.** As in task 2: add as a checklist item, linked work or a comment. A proposed status change on the decision ("superseded?") is shown, never applied.
5. **Task `suggest-risks`: not built.** It returns with Wave 10.
6. **Labels.** Every result reads "proposed by BMO" until accepted. The run log records the template id, version and settings.

## Tests

- **Prompts.** Built the same way twice. Refused without a scope.
- **System text.** Library text never appears in it (extend the existing test).
- **Answers.** The verifier marks canned answers correctly: one valid cite, one forged.
- **Decisions review.** The computed signal fires only for a decision whose rule has a finding; a decision with no rule is BMO-only and labelled proposed; a disagreement is pointed out.
- **Actions.** Each writes only when pressed. An engineer's accept goes into a draft.
- **Labels.** "proposed by BMO" is shown until a row is accepted.
- **Browser.** Pick entries, run with the fake backend, see dp's findings beside BMO's, add one result as a checklist item; run `check-decisions` on the demo's decisions.
