## Design [Proposal; rewritten after the owner answers]

1. **Template registry.** `prompts.ts` becomes a registry with one template per situation: explain-object, explain-relationship, explain-diagram, ask, challenge, draft-summary, decision-from-draft, plus the import tasks.
   - Each template has `{id, version, system builder, block plan, answer schema}`.
   - The preview shows `id@version`, and the run log records it.
   - `PROMPT_VERSION` goes to 2.0.0.
   - Templates live in code only and are never generated (★Q1.2).
2. **Context packs** (`src/assistant/contextPack.ts`, new). A pure function builds the blocks for a situation and its selectors.
   - The blocks come in a fixed order, and each block gets a share of the token budget.
   - Items are dropped whole, never cut, and the output is byte-identical for the same input.
   - The first block is a **manifest**: what is included, what is left out and why.
   - It adds the decisions about the referenced objects (`decisionsAbout`, `src/core/decisions.ts:614-616`).
   - It adds Markdown docs under the code root through the existing file gate (Q1.5).
   - Notes follow the lens as today in this wave. Wave 2 changes this: BMO always sees notes and comments (★Q2.2, DEC-092).
   - **Screen parity** (owner, 2026-11-19, DEC-094): every kind of thing the UI shows about a scope must have a place in that scope's pack, by default or through the lens and preview choices, and the manifest says what was left out and why. The pack builder is written so a new kind of data is added in one place. Known gaps today: comments (Wave 2), sticky notes (Wave 2), attachments (Wave 16). The re-anchor step (step 1) lists any other panel data that no pack carries, and adds it to this brief before step 3 starts. A computed test walks the fields the panels show for an object and checks each is in the pack or named in the manifest.
3. **Citation contract.** Text tasks answer `{statements: [{text, cites: [{kind, ref, lines?, quote?}]}], unknowns: [string]}`.
   - `kind` is one of model, file, decision, note, doc or fact. Wave 2 adds comment and sticky; Wave 16 adds attachment.
   - The schema goes to providers through `providerSchema`. The handoff `result.json` uses the same shape.
   - The answer arrives as a list of statements, so dp never needs to split sentences.
4. **Verifier** (`src/assistant/citations.ts`, new). It checks each cite **against the pack that was actually sent**, after redaction:
   - an object id exists in that model version;
   - the file and lines were inside a block that was sent;
   - a quote is found there, with whitespace normalised (reuse `findIn` from `review.ts`);
   - decision numbers, note ids, doc sections and fact ids exist.

   Each statement gets one status: cited, partly cited, general, no citation, or bad cite (★Q1.1).
   - A statement **refers to a thing** when its text names an object, relationship, file or path, decision, note, doc section or number that is in the pack. dp finds this by matching the pack's names, ids, paths and numbers in the text, so no LLM is involved.
   - A statement that refers to a thing needs a valid cite. One without it (no citation, or a bad cite) is **not shown in the answer**; it is listed under "N claims without a valid citation", which the person can open.
   - A statement that refers to nothing in the pack (a definition, advice) is shown, marked "general".
5. **UI.** Statements render with cite chips.
   - A chip only navigates inside dp: it reveals the object, opens the file panel at the lines, or opens the decision. It never opens a URL that the model wrote.
   - A header label reads "BMO · provider/model · N of M statements cited · not checked by a person".
   - Claims without a valid citation are collapsed under the answer ("N claims without a valid citation"), each marked "no citation" or "bad cite".
6. **Settings.** Temperature 0 where supported, and a seed where the API has one (OpenAI, Ollama). Both are recorded in the run log, and nothing promises a repeatable run (Q1.4).
7. **`docs/determinism.md`** (new). It holds:
   - the determinism classes (★A4);
   - the per-level table from questions 0.3;
   - one row per feature, which every later wave extends.
8. Fix DEC-065's path to `src/assistant/settings.ts`.

### 0.6 What makes a better fixed context prompt?

You asked that the prompts stay hard-coded for specific situations and never be written by an LLM. That is already how dp works [Fact]:
- every system text is a fixed TypeScript builder (`src/assistant/prompts.ts:130-261`, `PROMPT_VERSION` 1.0.0 at `:23`);
- data goes only into fenced, redacted blocks (`prompts.ts:42-53`);
- a test checks that system text never contains repository data (`tests/unit/bmo-core.test.ts:89`).

What makes a fixed prompt give better answers [Proposal, common practice]:

1. **One template per situation:** explain an object, explain a diagram, compare two versions, review drift, check anti-patterns, answer a question about dp. Each has an id and a version, shown in the preview.
2. **A fixed order:** the task, the rules, the shape of the answer, then the data from most to least important.
3. **A budget for each block**, so a big code excerpt can't push the model out. Whole items are dropped, never cut in half.
4. **A list of what was included, what was left out and why** ("12 files left out: budget"). The model can then say "I wasn't shown that" instead of guessing, which means fewer false positives.
5. **Stable ids for everything that can be quoted:** object ids, file and line, decision numbers, note ids. The answer cites them, and dp checks the citations.
6. **An explicit "say you don't know" rule**, with open questions at the end.
7. **Short worked examples, written by hand and kept in code**, for the hardest tasks.
8. **An evaluation set:** fixed inputs with known right answers, so a prompt change is measured, not guessed.

Proposed: Wave 1. See Q1.1 to Q1.4.

## The real-run gate (owner, 2026-11-20)

Until now every BMO test in the repository runs against canned answers; no real model has ever answered through dp, and the default model ids in `src/assistant/settings.ts` were never checked against a provider's current list (manual test plan U1 to U3). This wave defines the answer shape and the verifier that six later waves rely on, so it is the right place to see that it works against a real model, once.

- **What the gate is.** After steps 3 to 6 are built and green, run one real BMO text task (an `explain` of one demo container is enough) through **one route the owner will actually use**: a provider API key, a chat subscription through the handoff route (paste the prompt, paste the reply), or a local Ollama model. The result must pass the verifier, or be refused for a reason that is right (a forged cite, a missing quote), and the cited chips must open the right place.
- **Before it:** check the default model ids in `settings.ts` against the chosen provider's current list (U2) and fix any that are wrong. Credentials saved for the run are already sealed ([Wave 23](wave-23-sealed-credentials.md) is merged first).
- **Who:** the owner supplies the key or the chat app; the wave agent runs `dp bmo status` first and uses BMO if it is on (and tells the owner whether it was available), then walks through the run with the owner.
- **A pass or a fail is written into the review file** (route, model id, what came back, what the verifier said), with the row added to the manual test plan (U1, U3).
- **If no route can be tried** (no key, no chat app, no Ollama), the wave does not close: it stays at "built, gate open" in the README table, and Wave 25 and every BMO wave after it wait. Do not replace the gate with a canned-answer test.
- **Not in the gate:** the other two providers (they stay on the 1.0.0 checklist, section 4), scoring answers for quality (the deferred evaluation, ideas list I2.0) and cost.
