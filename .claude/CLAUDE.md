# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

designPerspectives is an MIT-licensed, model-based C4 architecture tool. One model (a Structurizr workspace on disk) feeds every diagram, and "lenses" present the same model differently per audience. Everything is TypeScript: a Node.js server (Hono) and the `dp` CLI in `src/`, and a React UI in `ui/` that is built into `static/` and shipped in the npm package. See [README.md](README.md) for the feature list and file formats.

## Commands

```bash
# Node 20.11+
npm ci                                      # installs and builds dist/ (prepare script)
npm test                                    # Vitest: unit + API + CLI tests (tests/unit/)
npm test -- tests/unit/ops.test.ts -t 'name'  # single test (tests/TESTS.csv has the exact command for each test)
npm run test:list                           # regenerate tests/TESTS.csv (one row per test); CI runs it with -- --check
npm run typecheck                           # tsc -p config: src, tests, scripts and config files in one check
npm run lint                                # ESLint (config/eslint.config.js) over src, tests, scripts, ui/src; lint:fix applies safe fixes
npm run format:check                        # Prettier (printWidth 200), enforced in CI (npm run format writes)
npm run dp -- serve [PATH]                  # dp from source: serves PATH/architecture/ on 127.0.0.1:8765 (creates an empty model if none; --demo creates the sample model and starts the demo system on ports 4200 to 4204)
npm run dp -- serve --read-only | --code-root SRC
npm run dp -- serve --allow-target-host HOST  # System Testing: let intercept points forward to HOST (repeatable; default this machine only)
npm run dp -- check                         # exit 1 on model problems (also drafts; warnings for missing code paths)
npm run dp -- diff --base main              # Markdown summary of model changes since a git ref
npm run dp -- scan [PATH] [--plan] [--prompt [--level c1|c2|c3]]  # codebase scan: no network, no model; writes architecture/import/ (evidence, analysis)
npm run dp -- import FILE [PATH] [--check]  # check a JSON import file, then make it a draft (dp import --schema prints the schema)
npm run dp -- bmo status|set|run TASK [PATH]  # BMO settings and runs; `run` sends nothing without --yes-send
npm run dp -- work list|add|import [PATH]  # linked work (WRK-02..088): pins to elements, relationships, diagrams, flows or the project; import takes SARIF, GitLab Code Quality, SonarQube issues or dp JSON, no network
npm run dp -- integrations list|set|remove  # tool connections for linked work status (.dp/integrations.json, architects only)

# UI (cd ui)
npm ci
npm run dev        # Vite on :5173, proxies /api to dp serve on :8765 (run dp serve alongside)
npm run typecheck
npm run build      # typecheck + vite build -> ../static/

# Browser tests (need the built UI; skip themselves if static/ is missing)
npx playwright install chromium             # or set DP_E2E_CHROME to a Chrome binary
npm run test:browser                        # Playwright, tests/browser/

npm run make-demo                           # regenerate bundled demo model (demo/)
```

Tool settings live in `config/` (the root keeps only `README.md`, `LICENSE`, `package.json`, `package-lock.json`, `.gitignore`): `tsconfig.base.json` with a small `tsconfig.json` in `src/` (also the build config: `tsc -p src` → `dist/`), `tests/` and `scripts/` so editors find the settings, `config/tsconfig.json` for the one-pass typecheck, `eslint.config.js` (run with `-c`, so its globs are relative to the repo root), `prettier.json` + `prettierignore`, `vitest.config.ts`, `playwright.config.ts`; `.vscode/settings.json` points the editor extensions at them. ESLint (typescript-eslint recommended + react-hooks) and Prettier are configured and both run in CI. CI ([.gitlab-ci.yml](.gitlab-ci.yml), GitLab, Linux with Node 20 and 22, PRO-10; `npm run ci` runs the same steps locally) typechecks, lints, checks formatting, runs vitest, fails if `tests/TESTS.csv` is stale, builds the UI, fails if the build changes `static/`, runs the browser tests, and fails if `npm run make-demo` changes `demo/` — so after changing model/ops/demo-related code, regenerate the demo and commit the result.

## Architecture

**Built UI is committed.** `npm run build` (in `ui/`) writes `static/index.html` and `static/assets/app.js`, `app.css`, `diagram-layout.js` (the lazily loaded elkjs) — fixed names, no content hash (tracked in git, shipped in the npm package). The server sends them with `Cache-Control: no-cache` and an `ETag`, so browsers revalidate (304 when unchanged). After UI changes, rebuild and commit `static/`, otherwise the served app and browser tests will be stale. `dist/` (compiled server/CLI) is not committed; `npm ci`/`npm install` builds it.

**Shared API types.** `src/shared/types.ts` is the API contract: the server functions return these types and `ui/src/types.ts` re-exports them (plus UI-only helpers). It must stay free of Node and DOM imports. Change a response shape there and both sides are checked by `tsc`.

**Data on disk** (per project, in `architecture/`):
- `workspace.json` — a Structurizr workspace (elements, relationships, views, positions, flows). Written with stable key order and formatting for clean `git diff`; IDs are readable slugs. Unknown fields are kept.
- `designperspectives.json` — the "sidecar": tag groups, lenses, characteristics list, cost settings, plus per-object `styles` and per-diagram `layouts`.
- Anything Structurizr has no field for is stored as `dp.*` element/relationship **properties** inside the workspace (full list in the [modelEdits.ts](src/core/modelEdits.ts) header). Add new per-object data the same way rather than inventing new files. The exceptions are `comments.json` (conversation about the model, not part of it: REC-01), handled by `core/comments.ts` and `server/routes/comments.ts`, with `ui/src/common/comments.tsx` on the UI side, and `checklist.json` (the checklist, REC-05), handled the same way by `core/checklist.ts` and `server/routes/checklist.ts`.

**Backend** (`src/core/`, `src/server/`, `src/demo/`, `src/cli.ts`):
- `workspace.ts` — read/check/write the Structurizr file format (`toWorkspace` normalises; `dumpWorkspace` writes known keys in a fixed order, drops empty defaults). `designPerspectivesFile.ts` — the sidecar model. `util.ts` — small shared helpers: atomic file writes and JSON helpers (`inlineJson` for `dp.*` property values, `roundHalfEven`).
- `modelEdits.ts` — **all edits go through here**; it is the single home of model rules (unique names per scope, unique relationship descriptions per pair, technology as a tag list). Errors are `ModelError` (shown to the user as-is, HTTP 422). New edit features belong here, with `server/app.ts` exposing them as thin routes.
- `diagrams.ts` — computes what each diagram shows *from the model* (like `include *`); diagram keys (`landscape`, `context-<id>`, `containers-<id>`, `components-<id>`, `code-<id>`, `connector-<relId>`, `flow-<name>`) are documented at the top. Higher levels show *derived* edges for lower-level relationships. Positions are stored in Structurizr units (UI value × 2). Also `syncViews` and `prune`.
- Planned change (Stage C, built): `codingPlan.ts` is the coding plan of a draft (`dp plan`): what to build, change, connect or remove, with a progress check against the code folder or a git branch. `modelUnits.ts` flattens a model into per-object units (element, relationship, view, position, tag group, lens, style, layout entry); `diff.ts` compares two versions (`ChangeSet`) and, for a diagram, marks its nodes/edges with `change` and adds removed objects as `ghost`s; `merge.ts` is the three-way merge used to apply a draft; `drafts.ts` manages `architecture/drafts/<id>/` (copy + `base/`); `git.ts` reads the model at a git ref (read-only, via the git CLI, DRF-05); `cliReports.ts` builds `dp check` results and the `dp diff` Markdown. Requests choose the version with headers `X-DP-Model` (`main`, `draft:<id>`, `ref:<git ref>`) / `X-DP-Compare` (`base`, `main`, `ref:<git ref>`) (DRF-04); `Project` takes an optional folder so each draft is a `Project` with its own undo history.
- `decisions.ts` — decision records (REC-04): `architecture/decisions/NNNN-slug.md`, a small fixed front-matter grammar (not YAML), parse/serialize that round-trips byte for byte, edit ops, checks and the renumbering used on apply. Decisions are part of the model: `Project.edit(fn(ws, sc, decisions))`, `dec:<file>` units, a `decisions` group in `ChangeSet`.
- `checklist.ts` — the checklist (REC-05): the store for `architecture/checklist.json`, the two shipped starter lists (`STARTERS`), BMO's questions from an import (`addFromImport`, called by `import/importer.ts`), and the answers as typed text for the import review (`typedAnswers`) and as feedback for BMO's next turn (`answerNotes`). `checklistRules.ts` — the checks dp makes itself for items with a rule, against the version shown (model rules) or `architecture/import/` (import rules).
- `homeSummary.ts` (home page summary, HUB-03), `catalog.ts` (shared catalog usage: linked copies, drift, data readers/writers, HUB-06), `credentials.ts` (integration credentials store, write-only values, optional AES-256-GCM with `DP_SECRET_KEY`, SEC-06), `history.ts` (git commits with model diffs per project, DRF-06), `work.ts` (linked work on any target: element, relationship, diagram, flow, project; list, set, push/upsert, WRK-02), `workStatus.ts` + `workTools/` (status refresh: one adapter per tool — github, gitlab, sonar, jira — with strict link matching and pinned API roots), `integrations.ts` (`.dp/integrations.json` tool connections, architects only), `workImport.ts` (SARIF, GitLab Code Quality, SonarQube issues and dp JSON reports → pushes, findings mapped to elements by code paths); `src/shared/workLinks.ts` (which connection a link belongs to); route module `routes/work.ts` (`/api/work*` list/target/items/import; the refresh stays in `model.ts`); the severity mapping (WRK-04) is the sidecar's `work.severity` (`cleanWorkSeverity` in `designPerspectivesFile.ts`, `PUT /api/work-settings` in `routes/sidecar.ts`, `severityOf` in `workLinks.ts`); work across projects (WRK-05) is `GET /api/hub/work` (`hubWork` in `routes/hub.ts`); CLI `dp work list|add|import` and `dp integrations list|set|remove`. `catalog.ts`'s `syncCopies` is run by `Hub.syncCatalog` so linked copies follow the catalog (HUB-07); per-project roles are `Auth.projectRole` (users file `projects`). Catalog/data edit ops (`addFromCatalog`, `linkCatalog`, `syncFromCatalog`, `cleanData`, `cleanAccess`) live in `modelEdits.ts`.
- `connectors.ts` (stages inside a relationship), `codeMap.ts` (the code level: maps components to files, scans Python/JS/TS imports, functions in a file), `codeFiles.ts` (where code is read from: the code root on disk, a draft's planned code edits, or a git commit; file paths confined to the code root, symlinks resolved), `flows.ts` (ordered steps over relationships ↔ Structurizr dynamic views), `backtrack.ts` (from a pipeline step or flow step back to its data source), `traces.ts` (OpenTelemetry trace files), `endpoints.ts` (matches an HTTP call to a relationship's `dp.endpoints`), `hosts.ts` (loopback and link-local host checks, shared), `validate.ts`, `users.ts` (the users file for the optional sign-in, password hashes). `server/auth.ts` is sign-in, sessions and roles (Stage P4, SEC-04).
- `src/shared/` also holds `decisionAlerts.ts` (which decisions need a look, shared by the home page and the Decisions page) and `secretFields.ts` (field names whose values are hidden in observed data).
- `project.ts` — `Project` (load, reload when files change on disk, `edit()` runs a change on a copy, syncs views/flows, validates, writes atomically; undo/redo stacks), `initProject`, package paths (`demo/`, `static/`).
- `src/demo/` — `demoHistory.ts` (the demo's git history) and `demoSystem.ts` (the demo system `dp serve --demo` starts: five tiny real HTTP services on ports 4200 to 4204 that call each other, serving the page in `demo/web-app/`; a `route` callback, which dp points at the open intercept points, says where each call goes).
- `server/hub.ts` — a hub of projects (HUB-04): `createHubApp(dir)` reads `hub.json`, builds each project's app lazily with `buildApp(root, {hub: true, auth, catalog})` and passes `/api/*` requests to the project named by `X-DP-Project`; it answers sign-in, the UI and the hub-level routes itself (`routes/hub.ts`: `/api/hub`, `/api/home`, `/api/catalog*`, and the integration credentials routes). A single-project `createApp` answers the same hub-level routes as a hub of one. Route modules capture `ctx` fields at registration, which is why each project gets its own app rather than a shared context.
- `server/app.ts` — `createApp(projectDir, {codeRoot, readOnly})` (= `buildApp(...).app`) only builds the shared context, installs the middleware, mounts the route modules in a fixed order (Hono matches in order) and maps errors to responses. `server/routeContext.ts` holds the shared `Ctx` (project, drafts, git readers, the per-request model version via `AsyncLocalStorage`, `writable()`/`edit()`) and the request-parsing helpers; `server/requestProtection.ts` the request protection (security headers, Host/cross-site checks, body limit, JSON-only, viewer role); `server/routes/` one `register<Area>(app, ctx)` per area: `readModel.ts` (state, diagrams, changes, undo/redo, history, backtracking), `drafts.ts`, `model.ts` (diagram positions, elements and relationships, flows, linked catalog copies, linked work status), `sidecar.ts`, `code.ts`, `decisions.ts`, `traces.ts` (the `GET /api/traces*` routes), `testing.ts` (the `/api/testing*` routes), `comments.ts`, `checklist.ts`, `hub.ts`, `import.ts` (the code import routes), `bmo.ts` (the BMO routes), and `ui.ts`, which serves the built UI. `cli.ts` — commander, entrypoint `dp`, binds 127.0.0.1 by default.

**System Testing** (`src/core/testing.ts`, `src/server/interceptProxy.ts`, `src/server/testSession.ts`, `src/server/routes/testing.ts`, RUN-06): an intercept point is a listener on 127.0.0.1 that forwards a caller's HTTP/1.1 calls to the address of the target (`dp.run.url`, RUN-07). `core/testing.ts` has no server imports: it holds the rules (which relationships a point covers, call matching, allowed targets, masking, breakpoints). Points resolve against the main model only, never a draft. `testSession.ts` is one session per project: points, run log, paused calls, breakpoints, watches; real values stay in memory and only `.dp/testing.json` (mode 0600, ports, breakpoints, watches, hold time) is written.

**Code import** (`src/import/`, COD-02, COD-03) brings a codebase into the model one C4 level at a time. Everything it produces ends in a draft, through `modelEdits.ts`. `scan.ts` reads the code only through a `CodeSource` and writes the facts to `evidence.json`; `knownServices.ts` is the shipped list of well-known external products that the scan matches; `intake.ts` holds the answers the code cannot give and the scan limits (`intake.json`); `analysis.ts` is the readiness analysis (candidates, decided, left, review effort); `schema.ts` is the import file schema (v1, `IMPORT_SCHEMA`) and its strict parser; `checks.ts` checks an import file against the model and the code and refuses errors; `importer.ts` turns a checked file into a draft in one `Project.edit` on that draft; `lastImport.ts` remembers what the importer last wrote, so a re-import keeps a person's edits; `review.ts` computes the review level (verified, partly verified, unverified) from checkable evidence and holds each item's decision, which the partial apply in `drafts.ts` uses; `importStatus.ts` is what the routes and `dp scan` share; `unmappedCode.ts` is the `dp check` warning for code that no component maps. Review data lives in `architecture/import/` and never in the model: the model carries no import label, confidence or evidence.

**BMO** (`src/assistant/`, COD-02, COD-08) is the optional assistant. It is off by default; its settings are `.dp/bmo.json` (mode 0600, outside git, changed by architects only). The server builds every prompt and chooses every file that may be read; a client sends only selectors. `tasks.ts` defines the tasks and checks each answer, `prompts.ts` holds the fixed system text and the data blocks, `modelText.ts` writes the model as text, `codeExcerpts.ts` ranks the code excerpts for a level, `redact.ts` picks the files and masks secret values, `importTasks.ts` builds the import tasks from the scan and the intake, and `runTask.ts` runs a task from its selectors. The preview returns the exact prompt and its hash; a run is refused unless the hash matches, so what was shown is what goes. `backend.ts` is the one-call interface. `handoffBackend.ts` writes the prompt to `architecture/import/handoff/` and calls no model. `providerBackend.ts` calls the Claude API, the OpenAI API or Ollama with plain `fetch` (pinned hosts, no redirects, one retry) and writes each run to `.dp/bmo/runs/`. `settings.ts` reads and checks `.dp/bmo.json`. `fakeBackend.ts` gives canned answers for tests only. Output is a proposal: a text answer is shown and not stored; an import file or a decision goes into a draft.

  - `lineShapes.ts` the line shape choices (names shown in the diagram panel and line menus); the per-diagram default is the sidecar `layouts[diagram].lineShape` (CAN-06, CAN-07).
  - `makeRoom.ts` Make room and Spread out (CAN-07): widen only the gaps that are too tight, or widen every gap about 20%.

## Repo notes

- `docs/README.md` indexes the docs. `docs/decisions.md` is the running list of decisions and their rationale: read it before changing a design choice, and add an entry (at the end of its topic) when a new decision is made. `docs/planned_features.md` holds planned work with a clear scope in a fixed entry format (open to contributors); the owner's private ideas live in `local/ideas.md` (git-ignored, the one place other products may be named). `docs/planned-change.md` is the how-to for the drafts workflow and its limits. `docs/notes/` holds chapter notes on the two reference books (C4 model; Fundamentals of Software Architecture) with `→ designPerspectives` implications.
- Each finished wave leaves a review file, `docs/waves/wave-NN-review.md` (PRO-21): what was built, how it was checked, limits, questions. The limits of the older stage reviews are section 31 of `docs/manual-test-plan.md`; the old `docs/reviews.md` was deleted on 2026-11-20 and is in git (`git show 24bbca1:docs/reviews.md`).
- `docs/CONTRIBUTING.md` is the one file for contributing, the code of conduct, reporting a security problem and the security model. `docs/CHANGELOG.md` lists changes per version.
- `demo/` holds everything for learning the tool (model, sample code, sample draft, demo hub, the demo system's page `web-app/`, `import-example.json`, `ci-examples/`); `demo/README.md` is the tour and carries the demo model's credits (Apache-2.0 attribution; keep it).
- `scripts/` holds `make-demo.ts` and `make-demo-hub.ts` (regenerate `demo/`; both write through `write-folder.ts`, which never leaves a half-written folder) and `list-tests.ts` (writes `tests/TESTS.csv`).
- `local/` (git-ignored) is for the owner's own files: reference books, notes.

## Working rules

- Everything is TypeScript. Do not add Python or other-language code.
- State trade-offs for design decisions. Separate sourced facts from interpretation, and say which is which.
- You may research other websites, tools and competitors (read their docs, pages and features) to inform design. Do not name or compare them in repository files, commit messages or pull requests; write the resulting ideas in our own terms.
